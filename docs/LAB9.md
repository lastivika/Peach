state access. Record its immutable `ws-...` ID. For later VCS runs set Terraform

### Remote automation without service account JSON keys

After the separately approved first apply creates federation, get the non-secret
outputs `hcp_workload_provider` and `hcp_service_account`. Set these HCP **environment**
variables in `peach-gcp-dev`:

```text
TFC_GCP_PROVIDER_AUTH=true
TFC_GCP_RUN_SERVICE_ACCOUNT_EMAIL=<hcp_service_account output>
TFC_GCP_WORKLOAD_PROVIDER_NAME=<hcp_workload_provider output>
```

Switch execution mode to Remote. Add the public Terraform inputs from the ignored
local tfvars as HCP Terraform variables (including workspace ID and workload flags).
Never upload ADC, `GOOGLE_CREDENTIALS` JSON or a service account key. The default
OIDC audience matches the configured provider name; do not override it casually.
An owner must bootstrap trust before HCP can authenticate; missing trust cannot
be solved by an initial unauthenticated remote apply. Runtime service accounts
have no infrastructure privileges. HCP's Terraform account can change project
IAM and secrets: protect apply permissions and trusted branches. Separate plan
and apply roles can further tighten this lab baseline.

Application image/Hosting automation is intentionally not an installed workflow.
HCP federation trusts HCP only, not arbitrary GitHub tokens. To automate app
releases later, create a separate WIF trust restricted to the exact repository,
branch/environment and deploy identity; grant registry writer, Hosting admin and
only the needed Run/job/act-as permissions. Do not reuse runtime accounts or
silently grant a GitHub workflow the HCP identity.

## First deployment sequence (requires future deployment authorization)

1. **Foundation:** with both workload flags false, approve the GCP-only plan and
   run `terraform -chdir=gcp apply`. This is the first billable step. It creates
   an empty database; no source data is copied. Enable Firebase on the existing
   project with `firebase login` then `firebase projects:addfirebase peach-lab9-2026`.
   If Firebase is already enabled, skip the add operation. Hosting content is
   managed by Firebase CLI, not Terraform; no second project is created.
2. **Image:** build from the same reviewed checkout that will be deployed:

   ```sh
   gcloud auth configure-docker us-central1-docker.pkg.dev
   IMAGE_TAG="us-central1-docker.pkg.dev/peach-lab9-2026/peach/backend:$(git rev-parse --short HEAD)"
   docker buildx build --platform linux/amd64 --target cloudrun \
     --provenance=false --tag "$IMAGE_TAG" --push backend
   gcloud artifacts docker images describe "$IMAGE_TAG" \
     --project peach-lab9-2026 --format='value(image_summary.digest)'
   ```

   Use a unique release tag if deploying a dirty tree; a commit tag alone does
   not identify uncommitted changes. Record the returned digest, then set `image`
   to `us-central1-docker.pkg.dev/peach-lab9-2026/peach/backend@sha256:...`.
   Never use a placeholder image, mutable `latest`, or an ARM-only image.

3. **Job:** set `enable_migration_job=true`, keep `enable_api=false`, then review
   and apply. Terraform creates the job but **does not execute it**.
4. **Migrate:** serialize deployments; do not execute two migration jobs together.

   ```sh
   gcloud run jobs execute peach-migrate --region us-central1 \
     --project peach-lab9-2026 --wait
   gcloud run jobs executions list --job peach-migrate --region us-central1 \
     --project peach-lab9-2026
   ```

   Require a successful execution and logs showing Alembic at revision `0005`.
   On failure keep API disabled, inspect logs without exposing secrets, correct
   the cause, then retry. Retries are disabled automatically. For later releases,
   set `migration_image` to the new digest and apply to update only the job,
   execute it successfully, then set `image` to the same digest and apply to
   promote the API;
   use backward-compatible expand/contract migrations. Terraform cannot infer
   job success. Do not run downgrade against live data as a routine rollback.

5. **API:** after migration success, set `enable_api=true`, review and apply.
   `terraform -chdir=gcp output -raw api_url` gives the actual endpoint. Keep the
   project/region fixed; the digest allowlist intentionally targets us-central1.
   Public invocation is expected: FastAPI validates Cognito tokens and owner scope.
   If organizational policy denies `allUsers`, stop and design an approved ingress
   solution; do not bypass that policy or remove application authorization.
6. **AWS prerequisites, separately approved:** the existing Cognito client must
   retain every old callback/logout URL and add:

   ```text
   callbacks:
     https://peach-lab9-2026.web.app/auth/callback/
     https://peach-lab9-2026.web.app/callback
     https://peach-lab9-2026.firebaseapp.com/auth/callback/
     https://peach-lab9-2026.firebaseapp.com/callback
   logout:
     https://peach-lab9-2026.web.app/
     https://peach-lab9-2026.firebaseapp.com/
   ```

   Current `infra/auth.tf` derives URLs from one AWS `site_url`; do **not** replace
   that value with Firebase (it would break the AWS site). Prepare a reviewed
   additive list change in the AWS workspace when authorized. Likewise extend
   parser function URL CORS to the Firebase origins, retaining AWS. No such AWS
   configuration was edited in this preparation. Cognito login is blocked until
   its URL list is updated. AI is optional and can remain explicitly unavailable.

7. **Frontend:** export public configuration in the shell, then build:

   ```sh
   export NEXT_PUBLIC_API_URL="$(terraform -chdir=gcp output -raw api_url)"
   export NEXT_PUBLIC_COGNITO_REGION=us-east-1
   export NEXT_PUBLIC_COGNITO_USER_POOL_ID='<existing pool ID>'
   export NEXT_PUBLIC_COGNITO_CLIENT_ID='<existing client ID>'
   export NEXT_PUBLIC_COGNITO_DOMAIN='<existing Cognito login domain>'
   export NEXT_PUBLIC_AGENDA_PARSER_URL='' # set existing URL only after CORS approval
   bash scripts/gcp/build-frontend.sh
   firebase deploy --only hosting --project peach-lab9-2026 --config firebase.json
   ```

   Variables are compiled into public JS, not read at Firebase runtime. Never put
   a client secret, access token or DB URL in `NEXT_PUBLIC_*`. Build requires Google
   Fonts access. Do not publish the local validation build using example IDs.
   Firebase hosts `frontend/out` using clean URLs, and retains the true 404 page.
   There is no SSR server or hidden mock API. Test Hosting locally with
   `firebase emulators:start --only hosting --project demo-peach-lab9` before release
   (local URL: `http://127.0.0.1:55009`; no cloud project is created).

## Verification and evidence

- `curl --fail "$NEXT_PUBLIC_API_URL/health"` returns liveness.
- `curl --fail "$NEXT_PUBLIC_API_URL/api/v1/health/ready"` verifies DB connectivity.
- Without a token, `/api/v1/items`, `/api/v1/me`, and `/api/v1/meetings` must reject
  access (401; missing auth configuration must fail closed with 503). Invalid,
  expired, wrong-audience and access-instead-of-ID tokens must fail.
- Preflight an allowed Firebase Origin and confirm the exact origin response;
  an unrelated origin must not receive an allow-origin header. CORS is not an
  authorization substitute.
- Hard-load `/items`, `/calendar`, `/home`, `/login/`, and `/auth/callback/`;
  verify callback query parameters survive Hosting routing and sign-in/logout
  returns correctly. Unknown paths must return the exported 404 page.
- Use two synthetic test users. Create/update/delete tasks and meetings, save a
  manual agenda, reload, and verify one user's IDs cannot read or mutate the
  other's data. Confirm timezone display and theme/UI behavior.
- If enabled, parse a synthetic agenda through the existing AWS parser, review and
  save it to GCP. If disabled, verify the existing unavailable message and manual
  editor. Do not imply that AWS reports contain GCP meetings.
- Capture non-secret Cloud Run revision/digest, successful job execution, Cloud SQL
  configuration and Hosting URL. Inspect logs for errors; redact user identifiers
  and tokens. No production data export or email test is authorized.

## Cost estimate and cleanup

Illustrative USD planning range: **$10–20/month** for a continuously running,
low-traffic lab, excluding existing AWS charges, tax and credits. The Cloud SQL
shared-core compute baseline is roughly $8–14 per 730 hours depending on current
regional SKU; add about $2 for 10 GiB SSD, plus backups/network. Run at minimum zero,
small image storage, Secret Manager, logging and Hosting may fit their free
allowances at lab traffic, but those allowances are shared and not guaranteed.
Verify the us-central1 selection in the official calculator immediately before
approval. A one-day demo pays roughly 24/730 of monthly compute, while storage and
other usage still accrue. Stopping SQL is not deleting it; storage remains billed.

Sources: [Cloud SQL pricing](https://cloud.google.com/sql/pricing),
[Cloud Run pricing](https://cloud.google.com/run/pricing),
[Artifact Registry pricing](https://cloud.google.com/artifact-registry/pricing),
[Secret Manager pricing](https://cloud.google.com/secret-manager/pricing),
[Firebase Hosting quotas](https://firebase.google.com/docs/hosting/usage-quotas-pricing).
The configured $5 alert cannot sustain this architecture for a full month and
will not shut resources down. No new budget or billing settings are provisioned.

For a future approved temporary stop/start of the GCP database (not executed now):

```sh
gcloud sql instances patch peach-postgres --project peach-lab9-2026 --activation-policy=NEVER
# Restart before using the app:
gcloud sql instances patch peach-postgres --project peach-lab9-2026 --activation-policy=ALWAYS
```

A stop makes API database calls unavailable and storage still bills. Coordinate
this with Terraform: its next plan may restore the running policy. No automatic
nightly stop schedule is installed.

Cleanup is destructive and requires separate authorization. Decide whether any
synthetic data or evidence must be retained, then set `deletion_protection=false`
and review/apply that change in **GCP only**. Use
`terraform -chdir=gcp plan -destroy` to review, then only after approval
`terraform -chdir=gcp destroy`. HCP federation permissions are managed by this
root; for reliable final teardown switch the workspace back to Local execution
and use authorized human ADC so destroying its WIF/roles cannot strand a remote
run. Never destroy `infra/` or the AWS workspace. Firebase CLI-managed Hosting
is outside Terraform: separately run
`firebase hosting:disable --project peach-lab9-2026` and review/delete retained
Hosting releases through Firebase before calling cleanup complete. Confirm SQL,
Artifact Registry images, secrets, jobs/service and retained backup costs in GCP.
APIs intentionally remain enabled; this does not itself incur usage charges.
Keep remote state history access restricted; it can retain old secret versions.
Do not delete the whole project or billing setup as an implicit cleanup shortcut.
